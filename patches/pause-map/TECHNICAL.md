# Pause map: technical notes

## Structure
- `zamn_pause_2mb.ips` (third-party, see Credits in the README) supplies the pause loop in bank `BE` (`BE:8000`, 560 bytes, plus a 39-byte hook) and the 2 MB expansion (header `$7FD7 = $0B`, zero fill, last byte `$FF`). `map/map.asm` adds the map on top. The expansion bytes are identical in every patch that needs 2 MB, so those patches can be applied in any order.
- The map runs inside the pause loop with NMI off: it has its own frame loop and its own joypad reads, saves and restores VRAM, CGRAM and the HUD, and returns to the pause screen.
- Memory: bank 7F holds the level's tile map from `7F:0000` up to its size (`$B2 x $B4` bytes, as far as `7F:EDFF` on levels 12 and 19), so the map uses nothing below `7F:EE00`. The VRAM it draws over (words `$45E0-$5037`, 5,296 bytes: its characters, the legend characters and the join prompt's two tiles) is kept 4 KB in the level layer's own tilemap (the 64 x 32 scroll ring at `$1B7E`, normally `$7800`) and 1,200 bytes in WRAM (`7F:F300-F6FF`, `7F:FF30-FFDF`). The level layer is off while the map is up.
- On exit the ring is rebuilt the way the game's scroll code (`80:A5E5`) builds it: each cell gets the level map word of the tile nearest the screen, plus priority when the tile number is below `$DC`, with no stop at the right edge (like the game). Cells of the visible window that differ from that (decals the game stamps into VRAM only, such as scorch marks; up to 77 seen on one screen) are recorded before the map opens (`7F:EE00`, 128 entries) and put back. Ring cells off screen are drawn again by the scroll code before they come into view.
- Level data is rendered at one pixel per tile into BG3 characters. Panning moves one cell (8 tiles) per step; each cell keeps a fixed character slot while the window moves over it, so only cells that come into view are redrawn. A full redraw takes about 0.3 s.
- Fog of war: `MarkFog` runs from a frame hook and records explored cells in `7F:FD00-FEFF`. There is deliberately no hook in the level loader (`80:86C8`): even a pass-through `JML` there shifts timing enough to desynchronize the attract demos. The array is cleared lazily when no player is active or the level number changes.
- Exit door: it is created only when the last victim is saved, so `82:F8DD` calls `ExitHook`, which records its position per player slot.
- Pause screen: the radar is dimmed with the rest of the screen (palette 4 gets a halved copy of palette 7 and the radar cells use it while paused), and L/R no longer toggle the radar there.
- A hidden chord on the map (A+B+L+R+Select) steps through whole map, whole map with item dots, and normal.

## Issues found and fixed
- **Joypad read race (found by bsnes).** Right after the vblank flag, `$4212` bit 0 (auto-read busy) is still clear until about dot 33 of the next line. A frame loop that waits for busy to clear could read `$4218` stale or half shifted. The map loop now waits for busy to rise (bounded) and then fall. Taps of two frames or more now close the map on all three emulators; a one-frame tap can still be missed.
- **Fog cleared on map reopen.** Two map variables sat inside the palette buffer and were overwritten when the map opened. They moved to `7F:FCC0-FCC2`.
- **Border garbage when patching an already-patched ROM.** An IPS only writes bytes that differ from the clean ROM, so zero bytes in the expansion were never written and stale bytes from an older build survived. The patch now writes whole spans (zeros included) in the expansion and always rewrites the legacy hook sites. Patching a clean ROM is still the recommended way.
- **Stray explored cells after a mid-level join (Save the Neighbors).** The save and OPTIONS scratch variables sat in `7F:FE00-FEFF`, the top of the explored-area array, so a join wrote junk that showed up as revealed map. They moved to `7F:EE02-EF07`; the array now holds exactly the 5 x 5 block around each player after a join.
- **Bottom of big levels overwritten (found from a player report on level 6).** The map backed up VRAM into `7F:E000-E06F` and `7F:E400-EFFF`, which is the end of the level's tile map on levels 6, 12, 18, 19, 32, 35, 40, 41 and 48 (their maps end between `7F:E100` and `7F:EE00`). Opening the map once replaced the bottom rows of the level, which then drew as a stray row of wrong tiles. Fixed by the layout above; the join prompt's buffers (`7F:E400-EB63`) moved out of that range too.
- **VRAM not fully restored.** The map drew over `$8BC0-$8FFF` without keeping it, and some levels load tile graphics there (differences after closing the map on levels 2, 6, 7, 8, 11, 18 and 22). It also wrote its VRAM read test into `$9000` before backing it up. The whole range is kept now, and the read test (and the join prompt's) writes into the ring row just above the screen, which is off screen and rebuilt.

## Known limitation
- The map's palette is chosen per 8 x 8 tile cell, so two markers of different colors inside the same cell (both players close together, or a victim next to a player) share one color. Moving a marker to avoid that would misplace it on the map, so they are left where they are.
- Considered and not done: drawing the two player markers as sprites, which carry their own palette and would remove the sharing. It means taking over the sprite layer the map switches off, borrowing a sprite tile and palette, and saving and restoring the game's sprite memory on exit. It could not be verified without hardware and only affects markers that share a cell, so the risk was not worth it.

## Testing
- Map opens, closes and the game resumes, with one and two players (Snes9x, bsnes, Mesen-S).
- Join prompt on levels 6, 12 and 19 (Snes9x; the level map part also on bsnes, level 12): the level map is unchanged after the prompt; VRAM is unchanged apart from the read test's off-screen words and what the game itself changes in the same frames (checked against a run without the prompt).
- Stack: memory just below the lowest stack point is touched to the same depth (`$1125`) as before the change.
- Panning on a level larger than the map window: identical results on all three emulators on level 2 (vertical), and on both axes on level 19 (Snes9x). Level 1 fits the window, so it cannot pan.
- Attract demos: rendered frames every 100 frames for 40,000 frames equal the original (0 of 400 checkpoints differ).
- Stack depth (bsnes with a lowest-stack counter): lowest stack pointer `$112A` with the map, `$1137` with the plain pause patch: 13 bytes more, inside the spare room.
- State after unpause: tilemap and palette identical to before the map opened.
- Map memory (Snes9x, every level 1-48, the bonus level (password BCDF), the credits level and bonus levels 53-55 (password XDSJ), three positions each): after open, pan and close, the level map in WRAM is unchanged and VRAM equals the model (unchanged outside the ring, the visible window of the ring unchanged, the rest of the ring as the scroll code builds it); the game keeps running. On bsnes (levels 1, 6, 12, 19 and 21) and Mesen-S (levels 1, 6 and 12), whose libretro cores do not expose VRAM, the check is by picture instead: the play area below the HUD is identical before the map opens and after it closes, the level map is unchanged and the game keeps running. (The HUD itself can differ by its own animation phase, because the map stops the game's frame interrupt; the build before this fix does the same.)
- The model was checked first with the original game: back up into the ring, overwrite the map's VRAM with random bytes, restore, rebuild, then play 1,540 frames and compare every frame with a run that never paused: 0 differing frames on all 53 levels.
- Combinations: see the table in the readme.
